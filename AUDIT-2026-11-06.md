## Context that shapes severity

This is a **public, read-only** dataset browser. The data (DPRK sanctions-evasion entities from UN Panel of Experts reports) is *intended* to be public — there is **no authentication, no user accounts, no sessions, no writes, no database, and no user PII**. That removes a large class of typical web-app risks by design: there is no login/CSRF surface, no secrets to leak, no SQL, no authorization model to get wrong. The permissive CORS (`*`) and the open, unauthenticated REST/MCP endpoints are deliberate and appropriate for public data.

Consequently the most severe finding is a **performance** issue, not a security one. The code is generally clean and security-conscious (see "What's already done well").

**Finding counts:** 1 Critical · 7 Moderate · ~9 Minor/trivial.

## 1. Security & Vulnerabilities

### Moderate

**S1 — No HTTP security headers.** *(confirmed live)*
`server.js` sets no `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`, or `Strict-Transport-Security`. The app renders dataset-controlled content (external links, Leaflet popups) and loads third-party tile servers, so a CSP is the key defense-in-depth here, and `X-Frame-Options`/`frame-ancestors` prevents clickjacking. Cloudflare may inject some in production, but the origin sets none.
→ Add `helmet` (or set headers manually) with a CSP that allows the Esri tile hosts and `'self'`.

**S2 — Dependency vulnerabilities (`npm audit`: 17 — 1 critical, 11 high, 5 moderate).**
Mostly transitive. The directly relevant one: `@modelcontextprotocol/sdk@1.29.0` (high) — *"HTTP server transports did not limit request body size or JSON-RPC batch length"*, which applies to your public `/mcp` endpoint. `express.json({ limit: '4mb' })` caps body size but not batch length. Also `compression` and `body-parser` DoS advisories.
→ `npm audit fix`; bump `@modelcontextprotocol/sdk` to ≥1.31 and re-test `/mcp`.

**S3 — Unsanitized `href` from dataset values.** `src/components/EntityDetail.jsx:98`, `src/components/GraphView.jsx:397`
Both render `<a href={value}>` where `value` is a dataset `sourceUrl`/`website`. React does **not** block `javascript:` / `data:` URLs in `href`, so a malicious value would execute script on click. The data is compiled by RUSI from UN reports (semi-trusted), so real-world risk is low — but the values are unvalidated.
→ Before rendering as a link, verify the scheme is `http`/`https`; otherwise render as plain text.

### Minor

**S4 — Leaflet popup built from string-interpolated HTML.** `src/components/MapView.jsx:99-105`
`circle.bindPopup(\`...${code}...${schemaBreakdown}...\`)`. Interpolated values are currently safe (2-letter country code, the fixed `schema` enum, and numeric counts), so there is no injection today — but it's an HTML sink that would become XSS if any interpolated field ever becomes free text.
→ Build the popup as a DOM element, or keep it strictly to the controlled values it uses now.

**S5 — CSV formula injection in export.** `src/utils/export.js:73`
`quote()` escapes quotes/commas/newlines but doesn't neutralize cells beginning with `= + - @`. Such a cell can execute as a formula when the CSV is opened in Excel/Sheets. The user downloads their own file, so impact is limited, but it's a one-line fix.
→ Prefix any cell starting with `= + - @` with a `'`.

**S6 — `X-Powered-By: Express` exposed.** *(confirmed live, on `/` and `/api`)* Minor version/stack disclosure.
→ `app.disable('x-powered-by')`.

### What's already done well (security)
No secrets in source; no `eval`/`dangerouslySetInnerHTML`/`innerHTML`; React auto-escaping covers all entity rendering; per-IP rate limiting on `/api` and `/mcp`; `trust proxy` set to `1` (not `true`) to prevent `X-Forwarded-For` spoofing; optional origin-lock (`ORIGIN_SHARED_SECRET`) to block direct-origin bypass of Cloudflare; JSON 404s for unknown `/api/*` paths; API `limit` capped at 500; `rel="noopener noreferrer"` on external links.

## 2. Performance & Core Web Vitals

### Critical

**P1 — The entire 21 MB (~4 MB gzipped) `data.json` is fetched and parsed client-side before anything renders.** `src/App.jsx:41`
*(Live check: gzip transfer = 4.05 MB.)* The app shows "Loading dataset…" until the full file downloads, JSON-parses, and is indexed into `entityMap` + `sanctionedIds`. This dominates **LCP and TTI** on every first visit (24h caching helps repeat visits only), and the dashboard — the landing view — needs only aggregate counts that `/api/stats` already provides. This is the single biggest issue in the app.
→ Heavy fix: drive the data-light views (dashboard, search, entity detail) from the REST API you already built, and lazy-load the bulk graph/map data only when those views open. Or ship a slimmed index for search and fetch full entities on demand. Minimum interim: render the dashboard from `/api/stats` immediately and defer the big fetch.

### Moderate

**P2 — No route-level code splitting; one unused heavy dependency.**
All views plus Leaflet (146 KB chunk) and d3-force ship in the initial paths (main bundle 215 KB). `react-force-graph-2d` is **declared in `package.json` but imported nowhere** — `GraphView` uses a hand-rolled canvas renderer — so it's dead weight that can be removed.
→ `React.lazy` the Map and Graph views; drop `react-force-graph-2d`.

**P3 — Each view re-scans the full dataset independently.**
`SearchPanel` builds a `_searchText` string for all 26k entities; `GraphView` builds its own `neighborMap`; `Dashboard`/`MapView` re-aggregate countries; etc. Each is memoized per-component but rebuilt on mount and not shared, causing TBT/jank on view switches.
→ Compute shared derived structures once (App-level or context) and pass down.

### Minor

**P4 — Server per-request scans (measured fine today).** `searchEntities` rebuilds search text each call and `findPath` rebuilds a 58k-edge adjacency list per `/api/paths` request (and does full-path-array BFS). Measured ~13 ms warm for search, so not a practical problem at current scale — but `findPath` can spike CPU/memory for distant pairs under load, and `dataLoader` already computes a `neighborMap` that `findPath` ignores.
→ Low priority: reuse the precomputed adjacency; store predecessors instead of copying whole path arrays.

**P5 — `index.html` served with `Cache-Control: public, max-age=3600`.** *(confirmed live)* Returning users can get a stale app shell for up to an hour after a redeploy (hashed assets + ETag mitigate asset mismatch, but the HTML entry itself lags).
→ Serve the HTML entry with `no-cache` (hashed assets keep their long cache).

## 3. UX & Accessibility (a11y)

### Moderate

**A1 — Primary interactions use `<div onClick>` with no keyboard/ARIA support.**
Search results, connection lists, map entity lists, path-finder nodes, graph legend toggles, and bookmark names are all clickable `<div>`/`<span>` with `onClick` but no `role`, `tabIndex`, or key handler (`SearchPanel.jsx:160`, `EntityDetail.jsx:123`, `MapView.jsx:147`, `PathFinder.jsx:131`, `GraphView.jsx:415`, `BookmarkPanel.jsx:45`). They are unreachable by keyboard and not announced as controls to screen readers. This is the highest-impact a11y gap.
→ Use `<button>` (reset its styles) or add `role="button"` + `tabIndex={0}` + `onKeyDown` (Enter/Space).

**A2 — Form controls lack associated labels.** `SearchPanel.jsx`
The main search input and the Type/Country `<select>`s rely on placeholder/visual context only — no `<label htmlFor>` or `aria-label`. Date inputs have adjacent text but aren't associated.
→ Add `aria-label` (or `htmlFor`/`id` pairs).

### Minor

**A3 — Low-contrast dim text.** `--text-dim: #5f8a68` on `--surface: #0a0f0b` is used widely for 11–13px secondary text, and the CRT scanline overlay (`opacity: .22`, `index.css:56`) further lowers effective contrast. Several of these likely fall below WCAG AA (4.5:1 for small text).
→ Measure the dim-text pairs; lighten `--text-dim` or enlarge the smallest uses.

**A4 — Fixed two-column grids don't collapse on mobile.** `EntityDetail.jsx:84` and `Dashboard.jsx:39` hard-code `gridTemplateColumns: '1fr 1fr'`, and `GraphView` uses a fixed 340px side panel. The viewport meta is present and most lists use `flex-wrap`, but these grids will cramp/overflow on phones.
→ Use `auto-fit`/`minmax` or a width media query.

**A5 — Canvas graph has no text/keyboard alternative.** Acceptable for a visualization, and the search/detail views expose the same data textually, which mitigates it — worth a note only.

**A6 — No `prefers-reduced-motion` handling** for the blinking cursor and scanline texture. Trivial nicety.

## 4. SEO / Discoverability

### Already strong
`index.html` has title, description, keywords, canonical, Open Graph, and a JSON-LD `Dataset` block; the server publishes `llms.txt`, `.well-known/openapi.json`, and a `robots.txt` that explicitly welcomes AI crawlers. This is a deliberate, well-executed "agent-ready" setup.

### Moderate

**SEO1 — Client-rendered SPA: crawlers see an empty `#root`.** All content renders in JS after the 4 MB fetch; the initial HTML has no body content. Google can render JS, but many social unfurlers — and some of the AI bots the `robots.txt` courts — won't execute JS or wait for a 4 MB payload. The rich head metadata compensates for the home page only; entity/search content isn't independently indexable.

**SEO2 — Hash routing gives no crawlable per-entity URLs.** Views/entities live under `#view=…` / `#entity=…`; fragments aren't distinct URLs, so individual entities can't be indexed or deep-linked for SEO. (Routing machine consumers to the API/MCP instead is a reasonable design choice — this is the tradeoff to be aware of, fixed only if entity-level organic discovery matters.)

### Minor

**SEO3 — No `og:image`** → social shares render without a preview image (`twitter:card` is `summary`). Add an image.
**SEO4 — No `sitemap.xml`** referenced from `robots.txt` (low value given hash routing).

## Remediation roadmap

### Quick wins (hours, low risk)
1. **S1** Add `helmet` + a CSP (allow Esri tile hosts + `'self'`); add `X-Frame-Options`/`frame-ancestors`.
2. **S2** `npm audit fix`; bump `@modelcontextprotocol/sdk` to ≥1.31 and re-test `/mcp`.
3. **S3** Scheme-validate `sourceUrl`/`website` before rendering as links.
4. **S5** CSV injection guard (prefix `= + - @` cells).
5. **S6** `app.disable('x-powered-by')`.
6. **A1 / A2** Convert clickable `<div>`s to buttons (or add `role`/`tabIndex`/`onKeyDown`); add `aria-label`s to search controls. *(Mechanical but touches several files.)*
7. **A4** Make the two-column grids responsive.
8. **P5** Serve `index.html` with `no-cache`.
9. **SEO3** Add `og:image`.
10. **Housekeeping** Remove `TimelineView` and the `react-force-graph-2d` dependency.

### Heavier / architectural
1. **P1 (top priority)** Stop shipping 21 MB to the browser: serve data-light views from the existing REST API, lazy-load graph/map data on demand, or ship a trimmed search index + on-demand entity fetch. Biggest win for Core Web Vitals *and* a prerequisite for meaningful SEO.
2. **P2 / P3** Route-level code splitting; compute shared derived structures once instead of per-view.
3. **SEO1 / SEO2** If entity-level organic discovery matters, add SSR/prerendering or static entity pages with real URLs. Otherwise, accept the API-first design and document it.
4. **P4** Precompute server-side adjacency for pathfinding (reuse `neighborMap`).
